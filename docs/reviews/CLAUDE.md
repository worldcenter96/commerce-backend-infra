# 아키텍처 리뷰 작업 규칙

## 1. 리뷰 목적
- 엔지니어가 작성한 docs/architecture.md가 docs/context.md의 요구사항을 충족하는지 세 명의 전문가 관점에서 독립적으로 검증한다.
- 리뷰는 설계의 타당성, 보안, 서비스 운영 가능성에 집중한다.
- 비용 및 비용 최적화는 리뷰 범위에서 제외한다.


## 2. 리뷰 담당 서브에이전트

### AWS 프로젝트 매니저 (aws-pm-reviewer)
- 10년 차 AWS 프로젝트 매니저의 관점에서 검토한다.
- context.md의 요구사항과 아키텍처 설계가 일치하는지 검증한다.
- AWS 서비스 선택 및 구성 방식이 기술적으로 타당한지 검토한다.
- 요구사항을 충족하지 못하거나 누락된 설계가 있는지 확인한다.
- 더 적합한 아키텍처가 있다면 선택 근거와 함께 대안을 제안한다.
- 불필요한 아키텍처 변경이나 과도한 설계 확장을 권장하지 않는다.

### 보안 담당자 (security-reviewer)
- 10년 차 보안 담당자의 관점에서 검토한다.
- 외부 및 내부 네트워크 접근 통제가 적절한지 검증한다.
- 데이터베이스, Redis, Bastion 등 주요 리소스의 보안 위험을 검토한다.
- TLS, 인증정보, 비밀정보 관리와 관련된 문제를 확인한다.
- 보안 요구사항 누락 및 잠재적 취약점을 식별한다.

### SRE 담당자 (sre-reviewer)
- 10년차 서비스 운영 담당자의 관점에서 검토한다.
- 실제 서비스 실행 및 운영이 가능한 아키텍처인지 검증한다.
- 네트워크 및 서비스 간 연결에서 발생할 수 있는 운영 문제를 확인한다.
- 배포 및 헬스 체크 구성이 적절한지 검토한다.
- 로그 수집, 모니터링, 장애 감지 가능성을 검토한다.
- 운영 중 발생할 수 있는 장애 위험과 관리상의 문제를 식별한다.


## 3. 리뷰 수행 원칙
- 세 서브에이전트는 동일한 context.md, architecture.md 및 아키텍처 다이어그램을 검토한다.
- 각 서브에이전트는 다른 리뷰어의 결과를 참고하지 않고 독립적으로 리뷰한다.
- 요구사항과 프로젝트 범위를 벗어나는 제안은 지양한다.
- 확인된 기술적 사실과 추론을 구분하고, 근거가 불충분하면 추가 검증이 필요하다고 명시한다.
- 문제를 발견하면 해당 요구사항, 영향, 기술적 근거 및 개선 방향을 제시한다.
- AI는 아키텍처를 직접 수정하거나 설계 결정을 확정하지 않는다.


## 4. 리뷰 결과 관리
- 리뷰 결과는 docs/reviews/R{번호}-YYYYMMDD-review-summary.md에 저장한다.
- 리뷰 대상 문서의 버전을 기록한다.
- 각 발견 사항에는 고유 ID, 리뷰어, 심각도, 관련 요구사항, 문제, 근거, 권장 조치 및 검증 상태를 포함한다.
- 심각도는 Critical / High / Medium / Low로 구분한다.
- 중복된 발견 사항은 통합하되 리뷰어 간 의견 차이는 보존한다.
- 기존 리뷰 결과를 덮어쓰지 않는다.


## 5. 의사결정 권한
- 리뷰 결과는 AI의 제안이며 확정된 설계가 아니다.
- 엔지니어는 발견 사항을 검증하고 수용 / 수정 / 거절 / 보류 / 위험 수용 여부를 결정한다.
- 엔지니어가 승인한 결정만 docs/ai-decision.md에 기록한다.
- 승인되지 않은 변경 사항을 architecture.md에 반영하지 않는다.
- 모든 리뷰 결과는 한국어로 작성한다.
